## Connection status and repeat authorization

The production applications response lists active grants only. The new frontend recognizes optional `expiredPlatforms` values and always prefers a current active grant over an expiry marker. The API would need to supply this account-level status even after Firestore removes expired grant records, and remove it on revocation or account deletion. An absent grant currently shows **Not connected** because it may have been revoked, expired or never created.

Repeat consent for the same OAuth client replaces that client’s grant. Each dynamic registration produces a fresh client ID and may produce a new confidential secret. If an assistant re-registers on each setup attempt, the grants appear separately. This follows client identity and can also represent legitimate independent connections. The frontend stops offering repeat setup after detecting any active grant for that provider. Existing grants stay individually visible and revocable. Provider names are selected using validated callback hosts, with unrecognized hosts grouped under **Other AI assistants**.

For a stronger duplicate guard, use a stable provider installation identity only when the provider supplies one that the server can verify. Otherwise make replacement an explicit first-party choice directed at a specific existing grant. The provider label, redirect host, display name and scope overlap are insufficient to identify duplicates. Leave approval settings on untouched grants intact. Keep reauthorization manual by default and never merge scopes or silently revoke grants.
