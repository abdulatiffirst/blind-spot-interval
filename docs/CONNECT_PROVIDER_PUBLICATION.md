## Connection status and repeat authorization

The applications API returns active grants and an `expiredPlatforms` list backed by server-observed grant expirations. It shows expiry for up to 30 days, with active grants taking precedence for their provider. Revocation clears expiry notices for the affected provider. The API does not infer provider-side disconnection or refresh-token expiry. Legacy records already removed by TTL cannot contribute to an expiry notice. The existing document TTL handles the retention window, and deleting the Blind Spot account removes the whole record.

**Connection details → Replace a connection** opens the assistant setup. Blind Spot consent then offers an explicit choice to keep or replace connections. It requires a choice when the incoming OAuth client already has an active grant. For a different client, it offers known same-provider connections, and the user can choose to keep them. An opaque authorization code carries the exact selected grant generation. Only successful token exchange can atomically revoke that grant and issue new tokens. Cancellation, failed token exchange, a changed target, account deletion or a global revoke leaves the replacement unauthorized. New grants use only the newly approved scopes and start with manual action approval.

Release the compatible Hosting consent UI before the updated API in the same approved rollout, so users can make the required choice as soon as the API supports it. Authorization codes from older versions still use their existing grant on the new API. A pending code created on the new API may require reauthorization after rollback.
